# Softmax 算子优化（昇腾 910B3 / Ascend C）

与上级目录的 Matmul 项目同源：**同一套方法论（版本化 + msprof 归因 + 双指标验证）**，但面对的瓶颈类型完全相反。

| | 另一个项目 Matmul | Softmax（本项目） |
|---|---|---|
| 计算单元 | Cube（矩阵单元） | Vector（向量单元） |
| 瓶颈类型 | **compute-bound**（计算受限） | **memory-bound**（带宽受限） |
| 算术强度 | ≈ 512 FLOP/B | **≈ 1.3 FLOP/B**（差 400 倍） |
| 优化主线 | 让计算别停下来等数据 | 让搬运遍数逼近理论下限 |
| 核间切分 | 受 16 元素对齐限制，只能用 16/20 核 | 行是天然切分单位，**40 核可满用** |

## 一、结果

固定条件：`M = N = 1024`，fp16 输入/输出、**fp32 中间计算**，沿行做 softmax；时长只计 kernel，`aclrtEvent` 夹 100 次连发取平均。

| 版本 | 核数 | 耗时 | 有效带宽 | 相对上一版 | 精度 `fro_err` |
|---|---|---|---|---|---|
| `v0` 朴素三遍遍历 | 1 AIV | 0.861923 ms | 4.87 GB/s | — | 1.06e-05 |
| `v1` 多核 | 40 AIV | 0.025499 ms | 164.49 GB/s | **33.8×** | 1.06e-05 |
| `v2` 一遍遍历 | 40 AIV | 0.019388 ms | 216.34 GB/s | 1.32× | 1.06e-05 |
| `v3` 行级双缓冲 | 40 AIV | 0.019620 ms | 213.77 GB/s | — （**负结果**） | 1.06e-05 |
| `v4` 归约去掉整行拷贝 | 40 AIV | 0.018730 ms | 223.93 GB/s | 1.04× | 1.06e-05 |
| `v5` 省掉 max 归约 | 40 AIV | 0.015064 ms | 278.44 GB/s | 1.24× | 6.41e-06 |
| `v6` 行级预取（基于 msprof） | 40 AIV | 0.014721 ms | 284.92 GB/s | 1.02× | 6.41e-06 |
| **`v7` 批式搬运（一次搬 8 行）** | **40 AIV** | **0.010570 ms** | **396.82 GB/s** | **1.39×** | **6.41e-06** |
| `v8` 归约收尾向量化 | 40 AIV | 0.010431 ms | 402.10 GB/s | — （**净零，弃用**） | 1.03e-05 |

**累计 81.5×**（v0 0.861923 ms → v7 0.010570 ms），全程 `test pass`。

> **v8 为什么是净零**：用 `WholeReduceSum` 把每行归约的收尾从 8 次标量读压到 1 次，msprof 显示
> **Scalar 4.68 → 3.52 µs（−25%）**，但 **Vector 4.70 → 5.66 µs（+20%）**——`WholeReduceSum` 本身是向量指令，
> 标量工作只是被搬到了同样饱和的 Vector 流水线上，总时间 10.54 → 10.55 µs 不变。
> 同会话三次对照也证实无差异（v7 均 0.010867 ms vs v8 均 0.010954 ms）。
> 因此最终版取 **v7**（同样快、精度更好、代码更简单），v8 作为"搬运工作不等于减少工作"的反例保留。

> **测量噪声提示**：softmax 跨会话测量有约 **5%** 波动（bench.sh 报过 0.010431，同代码直接连测为 0.010956）。
> 判断两个版本差异是否真实，必须在**同一会话内**连测三次，或看 msprof 的绝对时间。

有效带宽 = **4 MB（读 1 次 + 写 1 次，理论下限）÷ 耗时**。用它衡量"离硬件带宽还有多远"。

## 一之二、与 CANN 官方实现对比

官方数据由 `scripts/bench_official.py`（`torch_npu` → `aclnnSoftmax`）实测，口径相同（沿最后一维、必要流量 2·M·N·2 字节、device 侧 Event 计时）。

| 尺寸 | 官方耗时 | 官方有效带宽 | 本项目 |
|---|---|---|---|
| **1024×1024** | 33.16 µs | 126.48 GB/s | **15.06 µs / 278.44 GB/s（快 2.20×）** |
| 2048×2048 | 33.92 µs | 494.54 GB/s | 未测（kernel 的形状是编译期常量） |
| 4096×4096 | 101.25 µs | 662.81 GB/s | 未测 |

**一个关键观察**：官方在 2048 的耗时（33.92 µs）几乎等于 1024（33.16 µs），而带宽差了 4 倍。

```
1024:  33.16 us / 126.48 GB/s
2048:  33.92 us / 494.54 GB/s   <- 耗时几乎不变，带宽涨 4 倍
```

**这说明 1024 这个尺寸下，双方的时间都花在固定开销上，不是搬数据。** 这个判断直接决定了 v5 的方向：不去继续降流量（v2 已达下限），而是砍每行的固定开销。

### 剩余空间评估（ratio 的分母决定结论）

Softmax 是 memory-bound（算术强度约 1.3 FLOP/B，远低于机器平衡点 184 FLOP/B），
所以合理指标是 **有效带宽 ÷ 可达带宽**，而不是算力利用率（算它会被问"访存型算子算 FLOPS 干什么"）：

| 分母（可达带宽口径） | 数值 | 本项目 ratio | 折算还能快 |
|---|---|---|---|
| 理论 HBM 峰值 | 1600 GB/s | **17.8%** | 5.6× |
| 官方实现在大尺寸的可达带宽（4096²） | 662.8 GB/s | **43.0%** | 2.3× |
| 官方实现在**同尺寸**（1024²） | 126.5 GB/s | **225.3%** | 已超越 2.25× |

```
官方在 1024² 的 ratio = 126.5 / 662.8 = 19.1%
我们在 1024² 的 ratio = 284.9 / 662.8 = 43.0%     ← 同等尺寸约束下高 2.25 倍
```

结论与 Matmul 一致：**同尺寸下我们的 ratio 明显高于官方，剩余空间主要来自尺寸而非实现**。


## 一之三、逐版 msprof 数据与归因

每一版都用 `msprof op` 采过（40 核，`PipeUtilization`），CSV 原件在 `docs/prof/v<N>/`，用 `./scripts/sweep_prof.sh` 可一键重现。

**占空比**（每个核的平均值，取 40 核平均）：

| 版本 | aiv_time | Vector | MTE2(读) | MTE3(写) | Scalar |
|---|---|---|---|---|---|
| v0（1 核） | 918.49 µs | 43.5% | 46.5% | 15.8% | 12.8% |
| v1 | 25.98 µs | 40.5% | **52.4%** | 13.9% | 19.2% |
| v2 | 20.64 µs | 43.4% | **34.7%** | 17.0% | 25.3% |
| v3 | 18.47 µs | **47.2%** | 38.1% | 19.2% | 31.4% |
| v4 | 19.49 µs | 40.3% | 37.4% | 18.2% | **26.3%** |
| v5 | 16.19 µs | 34.7% | **45.4%** | 22.1% | 26.7% |
| v6 | 13.33 µs | 41.3% | **54.3%** | 27.1% | 31.2% |
| v7 | 10.54 µs | 44.6% | **15.5%** | 7.9% | 44.4% |
| v8 | 10.55 µs | **53.7%** | 16.2% | 8.4% | 33.4% |

**关键：占比会骗人，要看绝对时间。** 把占比乘回 `aiv_time`：

| 版本 | Vector | MTE2 读 | MTE3 写 | Scalar | 四项之和 | 实际总时间 | 重叠率 |
|---|---|---|---|---|---|---|---|
| v2 | 8.96 µs | **7.16 µs** | 3.51 µs | 5.22 µs | 24.85 | 20.64 | 83% |
| v4 | 7.85 µs | **7.29 µs** | 3.55 µs | 5.13 µs | 23.82 | 19.49 | 82% |
| v5 | 5.62 µs | **7.35 µs** | 3.58 µs | 4.32 µs | 20.87 | 16.19 | 78% |
| v6 | 5.51 µs | **7.24 µs** | 3.61 µs | 4.16 µs | 20.52 | 13.33 | 65% |
| **v7** | 4.70 µs | **1.63 µs** | **0.83 µs** | 4.68 µs | 11.84 | **10.54** | 89% |
| v8 | 5.66 µs | 1.71 µs | 0.89 µs | **3.52 µs** | 11.78 | 10.55 | 90% |

**v6 → v7 是本项目最漂亮的一次验证**：按"MTE2 绝对时间恒定 7.2 µs = 25.6 次 DataCopy × 约 280 ns
固定延迟"的推断，把"逐行搬"改成"一次搬 8 行"，MTE2 立刻从 **7.24 → 1.63 µs（−77%）**、
MTE3 从 **3.61 → 0.83 µs（−77%）**。**延迟模型的预测与实际完全吻合**，说明那个诊断是对的。

**v7 → v8 则是一次"净零"**：用 `WholeReduceSum` 压标量收尾，Scalar 确实从 4.68 → 3.52 µs（−25%），
但 Vector 从 4.70 → 5.66 µs（+20%）——`WholeReduceSum` 本身是向量指令，工作只是换了条流水线，
总时间 10.54 → 10.55 µs 不动。**"把工作搬走"不等于"把工作减少"。**

由此得到三条硬结论（每条都有数据支撑）：

1. **`v1→v2` 的收益来自 MTE2**：绝对时间 13.61 → 7.16 µs。一遍遍历真的把重复读干掉了。
2. **`v3` 零收益的真正原因**：v3 时 Vector 已占 47.2%（全场最高），而预取只能掩盖 MTE2（38.1%）——**掩盖非瓶颈项，收益必然为零**。之前从墙钟把它解释成"瓶颈不在搬运"，依据不对、结论碰巧对。
3. **`v4/v5` 的收益来自 Scalar 与 Vector**：Scalar 5.80 → 4.32 → 4.16 µs，Vector 8.72 → 5.62 → 5.51 µs。

**最关键的发现：MTE2 的绝对时间在所有版本里恒定在 7.1~7.35 µs，一动不动。**

而流量早在 v2 就降到了 4 MB 理论下限。所以这 7.2 µs **不是带宽，是延迟**：

```
每核 25.6 行 × 每行 1 次 DataCopy，每次只搬 2 KB（一行）
25.6 × 约 280 ns 固定延迟 ≈ 7.2 µs
```

同理 MTE3 的 3.6 µs 也是 25.6 次写、每次约 140 ns。

**这就直接给出下一版的方案：减少 `DataCopy` 的调用次数（一次搬多行），而不是继续降总流量。**


| 版本 | 上一版的瓶颈 | 证据 | 手段 | 结果 |
|---|---|---|---|---|
| v0 | 三遍遍历，每遍都从 GM 重读 | GM 流量 = 3 读 + 1 写 = **8 MB**（下限 4 MB）；单核 | — | 862 µs |
| v0 → v1 | 只用了 1 个 AIV | 40 核只用了 1 个 | 按行分核（`(M*blk)/blkNum` 余数分配） | **33.8×**，扩展效率 84.5% |
| v1 → v2 | **遍历遍数**：重复读 GM + exp 算两遍 | 流量 8 MB 是下限的 2 倍 | 整行驻留 UB，读一次算完写一次 | **1.32×**，流量降到理论下限 4 MB |
| v2 → v3 | （假设）MTE2 读与计算未重叠 | 每行仅 4 KB 数据，折算每核仅 5.2 GB/s | 行级双缓冲，预取下一行 | **0×（负结果）** |
| v2 → v4 | **每行固定开销**：两次整行拷贝 | v3 证明瓶颈不在搬运 | 归约首步直接读源，省两次整行拷贝 | 1.04× |
| v4 → v5 | **每行的两次归约**（各带一次 `V_S` 强制排空 + 8 次标量读） | 官方对标：1024 与 2048 耗时几乎相同，说明受固定开销而非带宽主导 | 省掉 max 归约（softmax 平移不变，见 `kUseMaxShift`） | **1.24×** |
| v5 → v6 | **MTE2 成了头号项（45.4%）**，且绝对时间恒定 7.24 µs | 占比乘回绝对时间后看到 MTE2 在 v2/v4/v5/v6 一直是 7.2 µs 上下不动 | **重新上 v3 的行级预取**——此时它掩盖的才是真瓶颈 | 1.02×（总时间 16.19→13.33 µs，但各项绝对时间未变，填的是气泡） |

**v3 与 v6 是同一手段、相反结果，这组对照最值得看**：
v3 时 Vector 占 47.2%、MTE2 只 38.1%，预取掩盖的是非瓶颈项 → 0 收益；
v5 把 Vector 压到 34.7%、MTE2 升到 45.4% 后，同样的预取 → 总时间降 18%。
**同一个优化手段，瓶颈不对就白做。**

**v3 为什么是负结果（值得记）**：流量已经降到理论下限之后，预取下一行没有任何收益，
说明那一刻的时间花在"等"，不在"搬"。这与 Matmul 项目里 `Kb=32` 那次的判断逻辑一致——
**瓶颈转移后，继续优化非瓶颈项收益确定为 0**。

## 三、两个踩过的坑（本项目最值钱的部分）

### 坑 1：向量操作数必须 32 字节对齐

树形归约里 `src[half]` 的偏移视图，当 `half` 降到 1/2/4 时，fp32 下的字节偏移只有 4/8/16，不满足 32B 对齐，**直接触发 AIV 异常**：

```
plog:  [vector core exception] ... retCode=0x31
       aclError 507035（表现在 aclrtSynchronizeStream 失败），输出全 0
```

修法：向量归约只做到 `stride >= 8`（32B = 8 个 float），余下 8 个元素在标量侧处理。

排查路径（每步都有对照）：去掉归约→正常；放大 `sharedTmpBuffer` 到 64 KB→仍崩；改成显式树归约→仍崩；改双 buffer ping-pong 消除别名→仍崩；**二分：保留归约、去掉 `GetValue`→仍崩**，才把范围锁定在归约本身。

### 坑 2：跨 pipe 复用同一 buffer 必须双向同步

`xHalf` 被 **MTE2 写入**、被 **Vector 读取**，且 v0 每行要写三次。只加 `MTE2_V`（写→读）不够，还必须加 **`V_MTE2`（读→写）**：

```cpp
AscendC::Cast(xF, xHalf, AscendC::RoundMode::CAST_NONE, N);
AscendC::SetFlag<AscendC::HardEvent::V_MTE2>(EVENT_ID0);   // ← 缺这行就出错
AscendC::WaitFlag<AscendC::HardEvent::V_MTE2>(EVENT_ID0);
```

否则下一遍的 `DataCopy` 可能在上一遍 `Cast` 还在读 `xHalf` 时就把它覆盖掉。

**症状极其迷惑**：约 40% 的行出错、其余行完全正确，看起来像随机竞态而非逻辑错误——排查时一度误判到归约和标量读取上。

定位手段：把 pass3 简化成「读 → 转 fp32 → 转回 fp16 → 写」的纯拷贝，输出本应严格等于输入，实测只有 **610/1024 行正确、最大绝对差 7.12**。最基础的数据通路就错，才把方向从"算法"扭到"同步"。

## 四、复现

```bash
./build.sh -c -n 6     # 全量编译当前版本（v6）；-n 可切 v0..v6 做逐版对比
./bench.sh 40          # 40 核跑
./bench.sh 1           # 单核（等价 v0 的核数配置）
./scripts/sweep_prof.sh            # 逐版采集 msprof，归档到 docs/prof/vN/
```

`bench.sh` 每次会往 `results.md` 追加一行（含版本、耗时、有效带宽、精度），日志落在 `logs/`。

**注意**：`-n` 切换内核版本后**必须带 `-c` 全量重编**（内核源文件变了，增量编译会链接失败）。
本次踩过：增量编译链接失败（`collect2: ld returned 1`），而 `bench.sh` 仍执行了旧的二进制，产出过一行"假 40 核数据"（v0 没有按行切分，40 核不会变快）。

## 五、已知边界与后续方向

| 项 | 说明 |
|---|---|
| **对可达带宽 ratio 59.9%** | v7 的 396.82 GB/s ÷ 662.81 GB/s（官方 4096² 可达）→ 还剩约 **1.67×**；对理论 HBM 1600 GB/s 则为 24.8% |
| **已解决：MTE2/MTE3 的固定延迟** | 按"25.6 次 `DataCopy` × 约 280 ns"的推断改成"一次搬 8 行"，MTE2 **7.24 → 1.63 µs（−77%）**、MTE3 **3.61 → 0.83 µs（−77%）**，总时间 13.33 → 10.54 µs |
| **当前瓶颈：Vector(4.70 µs) + Scalar(4.68 µs)** | 大头是每行的树形归约（25.6 行 × 5 步）与逐行归一化。下一步可试**用带 stride 的 Level-0 `Add` 一次归约 8 行**，把归约指令数降到 1/8；v8 只压了收尾（净零，见上） |
| **G 已接近 UB 上限** | `G=8` 占 104 KB；`G=16` 需 200 KB > 192 KB，装不下。所以批大小不能再加大 |
| **v5/v6 关掉了 max 平移** | softmax 对平移不变，`m` 只用于防 `exp` 上溢。本测试数据为 randn（`|x| ≤ ~5`），关掉安全且精度更好；**输入范围不可控时须把 `kUseMaxShift` 改回 `true`**（v4 就是开着的版本，可对照） |
| **大尺寸未测** | kernel 的 `M/N` 是编译期常量，尚未参数化；官方在 4096 能到 662.81 GB/s，我们在大尺寸的真实水平未知 |
| **归约仍可再优化** | 可用 `WholeReduceSum` / `WholeReduceMax` 的 mask 版本（`kernel_operator_vec_reduce_intf.h`），把最后 64→1 用一条指令完成，消除那 8 次标量读（Scalar 现占 4.16 µs） |
| **只支持单行驻留 UB** | 当前实现依赖"整行装得进 UB"（N=1024 fp32 = 4 KB）；N 更大时需行内分块 |
| **未做 bf16 支持** | 目前固定 fp16 输入 / fp32 计算 |
